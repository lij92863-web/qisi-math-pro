## 6. 当前已实现的固定流程和合同

内部 profile：`qwen37-simple-model-led-v1`。只支持完整、连续原页的 document 范围，不支持新 profile 的动态窗口/子集补读。

```text
原 PDF → 机械渲染全部原页
       → R1 … RP（先完成所有逐页原文转写）
       → L1 … LP（再完成所有逐页区域定位）
       → O（全来源一次纯文本整理）
       → C（本地按所有合法资产原框各裁一次）
       → V（一次独立复核：全部原页 + 候选 + 全部真实裁图）
       → 既有老师审核/采用/确认
```

单来源 P 页正常模型请求为 **2P+2**；S 个来源、总页数 T 时为 **2T+2S**。深圳 21 页单来源为 44 次。C 不调用模型。失败按边界停止，不自动填补或重试。

### R：原文保全

固定千问，单原页输入，`responseFormat:{type:'text'}`。完整返回字符串逐字保留，不要求模型同时交复杂结构。

即使文本包含 JSON、`table_data`、HTML、Markdown fence 或内嵌 bbox，也保留为不可信原始材料：不执行 HTML，不抽字段，不把内嵌坐标变为资源。请求绑定的 source/page 才是身份来源，正文不能冒充身份。

### L：模型专门定位，软件检查小合同

`pdf-page-regions-v1`，必填字段且禁止额外字段：

```text
location_version, source_id, page,
state: content | blank | unreadable,
regions: [{kind: figure | table | spatial,
           bbox: [left,top,right,bottom] 或 null,
           anchor: 字符串, issues: 字符串数组}],
issues: 字符串数组
```

框为归一化 0—1、有序有限数值；来源/页号必须精确一致。blank 不能携带区域；unreadable、null 框必须保留问题。机械 ID 由软件生成，只有合法 L 框能建立图资产。合同合法不证明模型没有漏图或裁框正确。

页证据包为 `pdf-page-evidence-v2`。每个 raw 页包含 source_id、page、page_image_hash、block_id、raw_text、attempt_id；保留原始 R/L 响应、定位、问题与资产。页图身份使用 data URL 的 SHA256。v1 恢复路径保留。

### O：模型承担整卷理解

全来源完整原文及定位资产标识/kind/anchor/issues交给模型，输出既有 `pdf-external-v2.2`。实际请求是纯文本白名单，不发送原页或裁图；不让 O 创造新 bbox。

跨页、分题、答案/解析归属、表格表达由模型完成；软件保留原来源/角色和既有序列验证，不用数学/语义猜测错挂。一个原页一个机械 block 不等于证明语义定位正确。模型提出 requests 只显示问题，不触发新请求。

### C 与 V：检查真实裁图和原文依据

每个非空合法 L 资产只裁一次；即使 O 未放置该资产，也裁取并交给 V，避免未使用图默默消失。同一资产被多处放置时共享图字节，标签记录 asset/source/page 和零到多个 placements。

软件不扩框、不改框、不重新识别。裁图技术失败阻止 V；本地已有 L 资产不额外发付费资源请求。

V 使用既有 review 合同，看全部原页、候选、所有实际裁图和定位问题，双向检查“原页有而候选漏了什么”“候选内容是否有原页依据”。V 只裁定，不返回修补正文/坐标，不触发后续修订模型。候选/裁图哈希变化使旧 pass 失效。之前的问题不因 O/V pass 自动清除。

### 缓存、账本、取消与机械容量

- 唯一既有账本在每次真实提交前登记，新增 transcribe/locate/organize/review 工序；R/L 费用按所有物理回执求和。
- 响应先保存回执和 usage，再做合同检查；received-invalid 也保留实际用量。
- 未知受理保留 `submission_unknown` 和费用预留，失败/取消的相同任务不能靠重跑暗中再付费。
- 可复用单元是完整来源 R+L 包；部分成功页只是证据，**不自动拼接/续跑**。完整包恢复重新校验原文、页序、身份和派生资产。
- O 配置变化可复用完整页包，旧版本不覆盖；缓存篡改拒绝，复核 pending/invalid 阻断后续来源。
- 取消不抹掉已收 usage，也不把仍未知的物理请求认作免费。
- system+prompt 最多 500000 UTF-8 字节，图像最多 256，maxTokens 不超过 65536；配置只能收紧。不会动态摘要/拆分。默认 maxTokens 与实测覆盖值应分别检查，实测使用 65536。
- 以上是机械容量检查，不保证供应商实际上下文/图像 token 可受理；真实任务还要冻结供应商能力和保守金额上界。

## 11. “为什么老是中断”：已知事实、推测和未做的事

### 已有证据支持的结论

直接技术故障是 HTTPS 连接发生 ECONNRESET。本机代理把连接失败包装成 HTTP502，不是供应商返回“识别失败”或模型合同拒绝。随后未知受理门禁按约定停止后续请求；这解释了整卷看起来中断，不代表识别本身正常。

最新 R1/R2 DNS 均指向 `198.18.0.136`。R1 有 TCP、正确 SNI、证书验证成功、TLS1.3 和 HTTP200；R2 TCP 约 3ms 后，约 50ms reset，没有观察到 TLS 成功或上游 HTTP 响应。

上一轮只读 Windows 路由查询显示：目标 `198.18.0.136` 经 **Meta** 接口，本机 `198.18.0.1`，下一跳 `198.18.0.2`。最近接口 index=4，较早记录曾为 38；不能硬编码 index 或把该路由归属直接认定为故障根因。

传输代码 [qisi-local-https-transport.js](../qisi-local-https-transport.js) 当前使用 `https.request`、`rejectUnauthorized:true`、**`agent:false`**。每次请求不复用连接，需要重新 TCP/TLS；新方案 44 次带来更多握手机会。这可能放大不稳定连接的暴露概率，但尚未证明就是 reset 根因。Node 行为参考：[官方 HTTPS 文档](https://nodejs.org/api/https.html#httpsrequesturl-options-callback)。

### 不能据此下的结论

- Meta 路由/DNS 相同的请求也成功；不能断定一定是 VPN、DNS、DashScope 或某个代理单方问题。
- 刚分配 socket 的 `servername:null` 不等于最终没有 SNI；成功请求也出现该初始值。
- 本地 `bytesWritten` 在 DNS/TCP 前已包含排队字节，不证明供应商已收到/计费。

- 不能承诺开启 keep-alive 就解决；复用也要验证连接失效、取消、超时和并发行为。
- 历史匿名连通探测成功，不证明连续 44 次真实传输稳定。
