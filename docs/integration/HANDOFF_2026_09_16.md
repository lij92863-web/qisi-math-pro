```text
                             deterministic MTEF acceptance and the 61-sample fidelity re-measure.
```

Environment gotchas learned the hard way:

- LibreOffice headless conversion needs an isolated profile:
  `soffice -env:UserInstallation=file:///<dir> --headless --convert-to pdf --outdir <dir> <file>`.
  The LibreOffice install on this machine had to be repaired from the MSI in `tmp/` (its `program`
  folder was empty, a broken upgrade).
- The browser harness blocks `**/api/ai/**` on purpose, and `https://` goes through
  `local-run-artifacts/r2-e2e-cdn-cache`; rebuild it with `node scripts/populate-e2e-cdn-cache.js`
  (pinned by `scripts/e2e-cdn-assets.lock.json`).
- `git commit -m "…$…"` breaks under PowerShell (the message gets mangled and git reports
  "did not match any file(s) known to git"). Keep commit messages free of `$`, backticks and quotes.
- Pushes sometimes fail with `schannel: failed to receive handshake` — retry once.
- `git status` may show `M app.js` while `git diff --stat` is empty; that is a line-ending artefact,
  the content equals HEAD. Verify with `git diff --stat`, not with status alone.
- The seal test compares `HEAD:app.js`, so it fails until the change is committed — that is expected.
  Whenever app.js changes, update `architecture/post-seal-approved-blobs.json` (git blob +
  content sha256) and the two ceilings in `tests/code-quality-boundaries.test.js` /
  `tests/app-shell-boundary.test.js`, then commit and re-run.

## 4. OPEN DEFECT (top priority) — wrong content on the wrong question

Real run of `周二晚测.docx`, final drafts:

```text
q2  stemLength=1260  A="横坐标缩短到原来的 1/2 （纵坐标不变），再将所得图象向左平移…"
q3  stemLength=1260  same A
q4  stemLength=1260  same A
q6  stemLength=1260  same A
q10 stemLength=1260  same A
q11 stemLength=1260  same A
q12 stemLength=1260  same A
(only q5, q7, q8 look like their own content)
```

Question 7's option set and its long stem are attached to seven other questions. This is exactly the
`DOCX SILENT WRONG CONTENT > 0` case the acceptance forbids.

Captured table sequence during the same run narrows the moment:

```text
table[13]  items q=2,3,4,5,6,7,8,10,11,12   optionCount: 0,0,0,4,0,4,4,0,0,0
table[16]  same items                       optionCount: 4,4,4,4,4,4,4,4,4,4   ← filled between here
table[18]/[19]                             type becomes 多选题 for all, answer empty
table[26]  final drafts                    stemLength 1260 for the seven contaminated drafts
```

So the defect lives between `table[13]` and `table[16]`: the item option-filling / merge step.
Leading hypothesis: the same `parsed`/`options` object (or the "best item") is being attached to many
items, or the merge is keyed by index instead of by question number. Also note questions 1 and 9
never appear in `table[13]` at all — they are missing from the parsed items, not filtered later.

Where to look next (verified anchors):

```text
app.js ~3250-3310   parsedList construction + console.table(...)   (the parsed-item table)
app.js  3180-3182   per-item 'parsed' / 'parsedOptions' logs
[BATCH_DEBUG][parsed] log site (label may be assembled, search for the string 'parsed' together
                     with BATCH_DEBUG rather than the literal "[BATCH_DEBUG][parsed]")
```

Acceptance for the fix: on the real paper the question-number set must be 1..12 (or the absent ones
must appear as explicit `missingQuestionNumbers`/`withheldItems`), and every question's stem and
options must come from that question; no two drafts may share an options object. Add regressions for
both, then re-run the real file, then the gates, then commit + push.
